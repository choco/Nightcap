# Nightcap

A macOS app that switches Night Shift off, or on, for chosen apps and websites: a Swift shell (`app/`) that owns every Apple API, around a platform-free Rust core (ADR-0001).

## Development

Work inside `nix develop`. It provides the pinned Rust toolchain, points cargo at Xcode's compiler and linker, and puts `scripts/` on `PATH`. CI runs the same scripts by path, so changing a script changes CI.

- `build-core [--release]`: builds the core and the CLI, and regenerates `app/NightcapCore` (the xcframework and the Swift bindings). The Swift side sees a change to the core's or the protocol's UniFFI exports only after this runs.
- `build-app [--release]`: builds `build/xcode/Release/Nightcap.app` or the dev build, `build/xcode/Debug/Nightcap Dev.app` (`io.github.choco.nightcap.dev`), unsigned. The dev build's own name keeps it apart from the installed app in System Settings.
- `run-dev`: builds, signs and launches the dev build.
- `run-tests`: runs the Rust tests. The core's integration tests (`crates/core/tests/`) stage cores in memory with `Scenario::stage()`, which only debug builds have, and reach the socket and the disk only in `ipc.rs`'s and `storage/file.rs`'s own tests.
- `test-app`: runs the Swift tests, the `NightcapTests` bundle, on its own: it never launches the app, and stages its cores in memory with `Core.staged`, which only a debug core exports, so run `build-core` without `--release` first.
- `sync-strings [--check]`: syncs the String Catalog, `app/Nightcap/Wording/Localizable.xcstrings`, with the strings the app's code uses, from the dev build's `.stringsdata`, which `xcodebuild` writes but never syncs itself: it adds the keys the catalog lacks, takes out those the code doesn't use and takes in the code's comments for translators, in Xcode's own style. Run `build-app` first, and give a new key its plural forms by hand. `--check` changes nothing, and fails if the catalog's keys, words or comments aren't as a sync would leave them, whatever its whitespace or order.
- `check [--rust] [--deps] [--audit] [--secrets] [--scripts] [--site] [--swift]`: runs what CI checks, every area unless flags name some: rustfmt, clippy, rustdoc and the tests (`--rust`), cargo-deny's licences, bans and sources against `deny.toml` (`--deps`), known vulnerabilities in the crates, the site's packages, the Swift packages and the workflows' actions, by cargo-deny, `pnpm audit`, OSV-Scanner and zizmor (`--audit`, which needs `GH_TOKEN` or `gh`'s login), betterleaks over every commit (`--secrets`), shellcheck on `scripts/`, `release/` and `.githooks/` and actionlint on the workflows (`--scripts`), `build-site` (`--site`), and swift-format against `.swift-format`, `build-core`, `build-app`, `sync-strings --check` and `test-app` (`--swift`, by default on macOS only). CI's jobs call it by area; `audit.yml` runs `--audit` daily, on a change to a lockfile or a workflow, and before a release. Dependencies are bumped when an advisory or a need calls for it: nothing proposes version updates.
- `.githooks/pre-commit`: refuses a commit whose staged changes hold a secret, by betterleaks, with what it finds redacted. `git config core.hooksPath .githooks` turns it on for every worktree of the clone; a false positive takes a `betterleaks:allow` comment on its line, or, once committed, its fingerprint in `.betterleaksignore`.
- `release-notes [<version>]`: prints a version's notes from `CHANGELOG.md`, written for users: under a `## 1.1.0 · 25 October 2026` heading, a one-paragraph headline, then New and Fixed. The commit that bumps the version adds them: the release workflow fails without them, and the site build fails on a heading in another shape. They become the GitHub release, Sparkle's update window and the site's changelog, which the notification the first launch after an update posts opens.
- `build-site`: installs, lints, type-checks and builds the project site into `build/site`, prerendered to static HTML. Preview it with `python3 -m http.server -d build/site`. The download buttons lead to the releases page unless `VITE_RELEASE_VERSION` and `VITE_RELEASE_URL` name a release's version and DMG, as the Pages deploy sets them.
- `render-dmg-background`: renders `release/dmg-assets/background.html` into the DMG's background PNGs, with Google Chrome. `release/dmg` builds the DMG from a signed app.
- `render-icons`: renders `app/icons/AppIcon.svg` into the app's icon set and the site's touch icon, and `TourSample.svg` into the tour sample's. The menu-bar moons are SVGs in `app/Nightcap/Assets.xcassets`, used as they are.
- `render-og-image`: renders the site's social card, `site/public/og.png`, from the built page, with Google Chrome. Render it again when the hero changes.

To compare the UI against a mockup, a dev build renders the settings window's tabs, onboarding's steps, the tour's panels and the pointer to the moon, light and dark, from a fixed scenario into a folder and quits: `NIGHTCAP_SNAPSHOT="$PWD/tmp/snap" "build/xcode/Debug/Nightcap Dev.app/Contents/MacOS/Nightcap Dev"`. Settings and onboarding draw cores it stages in memory, which reach each scenario by the core's own code; it needs no screen-recording permission (`app/Nightcap/Debug/SnapshotRenderer.swift`).

The site (`site/`) is React and TypeScript, built with Vite and pnpm, and prerendered at build time (`prerender.ts`), so each page arrives whole and React hydrates it. `pnpm --dir site dev` serves it, rendered the same way, with hot reload. Its pages are the home page, the privacy policy, the terms, the changelog (rendered from `CHANGELOG.md` by `plugins/changelog.ts`) and the 404 page that Pages serves for any missing path: `src/pages.ts` lists them, each with its head and its entry in `src/entries/`, which fill the same small HTML template per page, and `src/render.tsx` maps each HTML file to the page it prerenders. Neither `vite preview` nor `python3 -m http.server` serves `404.html` for a missing path the way Pages does: check the 404 page at `/404.html`. Tailwind styles its layout and type, themed from the design system's tokens; the drawn mocks (the macOS scene, menus, desk) keep their measures in CSS modules beside their components. `site/plugins/design.ts` writes `src/styles/tokens.css` from `design/tokens.json` and copies the app icon to `public/icon.svg`; both are build outputs.

The site's dependencies are pinned to exact versions at least two weeks old; `site/pnpm-workspace.yaml` enforces the age for transitive ones too. Biome lints and formats the site with its recommended defaults (`pnpm --dir site check`, and `pnpm --dir site format` to apply fixes); it stands in for ESLint because typescript-eslint doesn't support TypeScript 7 yet.

The site's ambient motion is free in Safari only while WebKit's compositor runs all of it. A single animation WebKit runs on its main thread (a `reverse` direction, an animated `box-shadow` or mask, a script loop), any listener for animation events (`src/hydrate.tsx` turns React's away), or a moving layer the page's size with pixels to draw has it restyle every animated element on the page, every frame: the doodles then cost a sixth of a core. A transition, even of opacity, keeps that main thread busy for as long as it runs, the more so the more animations the page has, and one of `box-shadow` or a colour about three times as much: a demo that loops while in view, as the Desk and the Shortcut do, costs a few percent of a core. Keep motion to transform and opacity keyframes, move things after the first paint only by transform (a box that changes its size or place is a layout shift, which Lighthouse scores in Performance and in Agentic Browsing), and check a change's idle CPU in Safari and its CLS in Lighthouse.

The privacy policy (`site/src/Privacy.tsx`) says what Nightcap keeps, where, and what it sends over the network. A change to any of these, in the app or the site, changes the policy and its date in the same commit.

Swift files under `app/Nightcap/` join the app target automatically, and those under `app/NightcapTests/` the test bundle (folder-synced groups); an app file the tests compile too, such as `Onboarding/OnboardingFlow.swift`, is listed in the `Nightcap` folder's exceptions for `NightcapTests`. Otherwise the project file changes only for settings, build phases and packages. Signing goes through `release/sign` alone, with Xcode's own signing off. `build/`, `target/`, the xcframework and the Swift bindings in `app/NightcapCore/Sources` are build outputs: change their sources and rebuild.
